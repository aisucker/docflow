# Архитектура

## Выбор модели

DocJet использует модульный монолит. API, workflow и фоновые задачи находятся в одном исполняемом процессе Go, но отделены независимыми таблицами и HTTP-ресурсами. Такая конструкция упрощает разработку и транзакции согласования. Интеграции получают события из таблицы outbox.

## Согласование

1. Автор создаёт документ со статусом `draft`.
2. Автор или регистратор выбирает подходящую активную схему и вызывает `POST /documents/{id}/start`.
3. В одной транзакции блокируется документ, создаётся workflow_instance со снимком определения, статус меняется на `in_review`, на первом подходящем этапе создаются задачи для указанных участников.
4. Согласующий отправляет решение. Backend блокирует экземпляр маршрута, проверяет принадлежность задания и актуальный статус, фиксирует решение.
5. При `all` переход выполняется после решений всех участников. При `any` — после первого согласования. При отклонении или возврате остальные задачи этапа отменяются.
6. Когда этап завершён, engine пропускает этапы с ложным условием и создаёт задания следующего подходящего этапа. При достижении конца маршрут и документ переходят в `approved`.
7. При возврате автор может исправить поля, а затем запустить новый экземпляр. История предыдущего запуска остаётся.

Выполнение маршрута НЕ зависит от открытой вкладки браузера. Frontend не решает, кому назначить задание, когда переводить этап и допустимо ли согласование; он только показывает состояние и отправляет команды.

## Границы ответственности

- `document_types`: схемы реквизитов. Изменения схемы распространяются на последующее редактирование; следует избегать удаления используемых обязательных полей без плана миграции.
- `workflow_definitions`: иммутабельные версии маршрутов; при редактировании создаётся новая строка.
- `workflow_instances`: снимок маршрута и указатель текущего этапа.
- `workflow_tasks`: задания для пользователей; статусы истории остаются даже после завершения документа.
- `document_events`: аудит, в том числе комментарии согласующих и технические переходы.
- `outbox`: события для интеграций, доставляемые фоновым обработчиком.
- `files`: метаданные версий; фактические данные находятся вне БД.

## Индексы

Индексы `documents_journal_idx`, `documents_type_idx`, GIN по `fields` и поисковый по текстовым атрибутам; `workflow_tasks_assignee_idx` для очереди задач; `document_events_doc_idx` для истории. При росте нагрузки следует заменить поиск `ILIKE` на полнотекстовый индекс или отдельный поисковый движок.

## Эксплуатация

Версия миграции хранится в `schema_migrations`. Сервис блокирует миграции advisory-lock, чтобы параллельные старты не изменяли DDL одновременно. Для промышленной эксплуатации стоит выделить миграции в отдельный deploy job, а доставку webhook — в выделенный worker. Масштабирование API в несколько реплик до переработки механизма выбора строк outbox не рекомендуется.
