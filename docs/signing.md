# ЭЦП НУЦ РК и NCALayer

В маршруте доступен тип этапа **«Подписание ЭЦП»**. Задача не может завершиться обычным запросом «Выполнить»: сервер требует проверенную CMS-подпись.

## Настройка

1. Запустите собственный NCANode 3.5.1. Для локальной установки подготовлен `outputs/Start-SigningService.ps1` рядом с рабочим каталогом проекта. Общие скрипты запуска и остановки DocFlow также управляют этим сервисом.
2. Задайте серверу DocFlow `NCANODE_URL=http://127.0.0.1:14579`. В Docker адрес указывает на сервис внутри вашей сети. Не используйте публичные демонстрационные серверы для рабочих документов.
3. В разделе «Пользователи» откройте существующего сотрудника и укажите его **ИИН для подписи НУЦ РК**. Это поле изменяет только администратор; оно не возвращается другим сотрудникам через каталог пользователей.
4. Добавьте в маршрут этап «Подписание ЭЦП», назначьте подписантов и сохраните новую версию. Существующие запущенные маршруты сохраняют свой снимок.
5. На компьютере подписанта установите и запустите [NCALayer](https://pki.gov.kz/ru/ncalayer/). Закрытый ключ и пароль выбираются в NCALayer; сервер DocFlow их не получает.

## Что подписывается

Подписывается JSON-пакет `docflow-signing-v1`: карточка документа, проектный и регистрационный номера, идентификаторы маршрута и задачи, одноразовое случайное значение и SHA-256 последних версий каждого вложения. При отсутствии файлов подписывается карточка.

Пакет хранится сервером, действует 10 минут и доступен назначенному подписанту. NCALayer через `kz.gov.pki.knca.basics/sign` создаёт отдельную CMS-подпись с запросом метки времени. Подпись относится к пакету; это не встроенная подпись PDF/PAdES и не отдельная CMS-подпись непосредственно байтов PDF/DOCX.

Перед завершением задачи сервер проверяет неизменность карточки и файлов, затем передаёт CMS и точный пакет вашему NCANode `/cms/verify` с проверками OCSP и CRL. Требуются положительный криптографический результат, статус `VALID`, действующий сертификат `SIGN`, подтверждённый статус отзыва и совпадение ИИН сертификата с ИИН назначенного сотрудника. При ошибке проверки задача остаётся незавершённой.

Сохраняются CMS, исходный пакет, его SHA-256, сертификат подписанта и отчёт проверки. CMS и пакет можно скачать из карточки. Историческая подпись подтверждает сохранённый пакет на момент подписания; изменение документа после возврата не изменяет этот пакет. Повторный этап требует новой подписи.

Сервис проверки должен иметь сетевой доступ к службам НУЦ РК и актуальные доверенные корневые сертификаты. Локальный запуск использует HTTPS-источники сертификатов с портала НУЦ; проверка TLS не отключается. Отсутствие сети/данных проверки не считается успешным подписанием.

## Проверка

Состояние: `GET /api/v1/signing/status` (после входа). Реальный выбор ключа и подписание выполняет сам владелец ЭЦП. Серверные тесты используют отдельную базу и явно обозначенный макет проверяющего сервиса; они не заменяют контрольный проход с реальным сертификатом.
