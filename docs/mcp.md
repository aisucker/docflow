# Docflow MCP

Отдельный сервер на Go предоставляет 25 инструментов для работы с Docflow из совместимого ИИ-клиента. Транспорт — **stdio**: клиент запускает `docflow-mcp.exe` и общается с ним через stdin/stdout. Постоянно запускать его отдельным окном не нужно. REST API Docflow должен быть запущен.

Используется [официальный MCP Go SDK](https://github.com/modelcontextprotocol/go-sdk/tree/v1.8.0), версия зафиксирована в отдельном модуле `mcp/go.mod`. Для сборки нужен Go 1.25 или новее; основной сервер Docflow сохраняет собственный модуль и зависимости.

## Сборка и проверка

Из корня репозитория:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\mcp\build.ps1
.\mcp\docflow-mcp.exe --config-file .\local-config.json --check
```

Для Linux/macOS: `cd mcp && go build -o docflow-mcp ./cmd/docflow-mcp`.

`--check` проверяет вход и выводит имя и роль в stderr. Пароли и токены не печатаются. Файл `local-config.json` существующей Windows-установки подходит для локальной проверки, но подключает ИИ под указанной в нём учётной записью — обычно администратором. Для повседневной работы используйте собственную учётную запись сотрудника.

## Подключение

Создайте `mcp/config.local.json` по образцу `mcp/config.example.json`, указав адрес API и существующие email/пароль пользователя Docflow. Файл с секретами исключён из Git. Не вставляйте пароль в чат с ИИ.

Пример конфигурации клиента с форматом `mcpServers`:

```json
{
  "mcpServers": {
    "docflow": {
      "command": "C:/path/to/docflow/mcp/docflow-mcp.exe",
      "args": ["--config-file", "C:/path/to/docflow/mcp/config.local.json"]
    }
  }
}
```

Замените пути на абсолютные. Если клиент использует другой формат настроек, укажите тот же исполняемый файл и аргументы в его интерфейсе добавления stdio-сервера. Готовый образец — `mcp/client.example.json`.

Для этой локальной Windows-установки также доступен `mcp/Start-DocFlow-MCP.ps1`: он читает `../local-config.json` и запускает бинарный файл. В клиенте укажите команду `powershell.exe`, аргументы `-NoProfile`, `-ExecutionPolicy`, `Bypass`, `-File`, абсолютный путь к этому скрипту. Можно передать `-ConfigFile` и `-ReadOnly`.

Не запускайте скрипт обычной двойной кнопкой: без клиента процесс будет ждать MCP-сообщения.

## Авторизация

Поддерживаются переменные среды, переопределяющие JSON:

| Переменная | Значение |
|---|---|
| `DOCFLOW_API_URL` | Корень API, по умолчанию `http://127.0.0.1:8080`; можно `/api/v1` |
| `DOCFLOW_CONFIG_FILE` | Путь к конфигурации вместо `--config-file` |
| `DOCFLOW_EMAIL`, `DOCFLOW_PASSWORD` | Существующая учётная запись |
| `DOCFLOW_ACCESS_TOKEN` | Пользовательский access token; без refresh после истечения нужен новый |
| `DOCFLOW_REFRESH_TOKEN` | Пользовательский refresh token; ротируется в памяти, не делите его с другой сессией |
| `DOCFLOW_MCP_READ_ONLY` | `true` скрывает инструменты записи и блокирует изменяющие API-запросы |

Вход создаёт обычную сессию Docflow. Access token обновляется через refresh с сериализацией параллельных запросов. Созданная процессом сессия отзывается при штатном завершении; после аварийного завершения действует обычный срок сессии. Токены сохраняются только в памяти. Переданный извне refresh token ротируется и не записывается обратно в файл: для повторного запуска предпочтительнее email/пароль или отдельный свежий токен.

Старые интеграционные токены `dfi_` не подходят для полного MCP: у них нет доступа к пользовательским задачам и справочникам. MCP не расширяет их права. Пароль PostgreSQL, APP_SECRET и ключи ЭЦП этому серверу не нужны.

HTTP разрешён только для loopback; удалённый API требует HTTPS. Перенаправления и системный HTTP-прокси отключены, чтобы токен не ушёл на другой адрес. MCP сам не публикует сетевой порт и не реализует удалённый HTTP/OAuth endpoint.

## Инструменты

| Группа | Инструменты |
|---|---|
| Учётная запись | `docflow_get_me` |
| Справочники | `docflow_list_document_types`, `docflow_list_users`, `docflow_list_departments`, `docflow_list_positions`, `docflow_list_groups`, `docflow_list_journals`, `docflow_list_templates`, `docflow_list_workflows` |
| Маршруты и журналы | `docflow_get_workflow`, `docflow_list_journal_entries` |
| Чтение документов | `docflow_list_documents`, `docflow_get_document`, `docflow_get_document_route`, `docflow_get_document_workflow`, `docflow_get_document_history`, `docflow_list_document_files`, `docflow_list_document_signatures` |
| Изменения | `docflow_create_document`, `docflow_update_document`, `docflow_start_workflow`, `docflow_generate_document_file` |
| Задачи | `docflow_list_tasks`, `docflow_decide_task`, `docflow_delegate_task` |

В режиме чтения остаётся 19 инструментов. Справочники поддерживают поиск и страницы `offset/limit` (до 100 элементов). Документы и задачи ограничены возможностями текущего REST API: документы — до 100 последних совпадений, задачи — до 100; полного постраничного обхода этих списков пока нет.

Ресурс `docflow://guide` и инструкции сервера объясняют порядок работы, структуру полей согласования и ограничения. Ответы содержат JSON одновременно как текст и `structuredContent.data`; ошибки API помечаются `isError` и сохраняют HTTP-статус.

## Примеры поручений ИИ

- «Посмотри типы документов и какие реквизиты обязательны для служебной записки».
- «Найди сотрудника по имени и покажи его подразделение».
- «Создай черновик служебной записки с таким содержанием и указанными согласующими».
- «Покажи мои ожидающие задачи и доступные действия».
- «Выполни мою задачу по этому документу с комментарием».
- «Поручи мою задачу указанному сотруднику».
- «Покажи ход согласования и историю документа».

Создание документа и отправка по маршруту — отдельные инструменты. Решения проверяются сервером: даже администратор не может выполнить чужую задачу. Поручение работает как в интерфейсе: исходный исполнитель сохраняет право выполнить задачу, первое решение закрывает парную задачу. Тексты документов и комментарии считаются данными, а не инструкциями для ИИ.

Перед редактированием ИИ получает свежую карточку и передаёт её `updated_at` как `expected_updated_at`. Изменяются только указанные реквизиты; `fields` объединяется с существующими ключами, `null` удаляет ключ. Сервер проверяет время изменения под блокировкой строки: устаревшее сохранение получает 409 и не затирает данные.

Изменяющие операции не повторяются автоматически после сетевой ошибки; сначала нужно проверить карточку и историю. Единственный повтор — после подтверждённого 401 с успешным обновлением сессии. Повторное самостоятельное создание черновика всё ещё создаёт новый документ: клиенту следует учитывать это при восстановлении после сбоя.

Подпись ЭЦП не автоматизируется: владелец ключа подписывает в NCALayer. MCP не принимает закрытые ключи и не обходит проверку CMS. Удаление документов, изменение учётных записей и прав, выдача токенов, произвольные HTTP/SQL-запросы и доступ к локальным файлам инструментами не предоставляются. Вложения можно просматривать как метаданные и генерировать из существующих шаблонов; загрузка/скачивание бинарного содержимого не входят в эту версию.

## Проверки

```powershell
cd mcp
go test ./...
$env:DOCFLOW_MCP_BINARY = (Resolve-Path .\docflow-mcp.exe).Path
go test ./internal/docflow -run TestStdioBinary -v
```

`TestLiveMCPWorkflow` предназначен только для отдельного API с временной базой `docflow_test_*`. Нужны `DOCFLOW_MCP_TEST_API_URL`, `DOCFLOW_MCP_TEST_EMAIL`, `DOCFLOW_MCP_TEST_PASSWORD`, `DOCFLOW_MCP_TEST_ALLOW_WRITES=isolated-database`. Тест создаёт фикстуры, документ и маршрут, проверяет частичное редактирование, конфликт версии, недоступность чужого документа, согласование, поручение и завершение задачи другим сотрудником. Не запускайте его против рабочей базы.

## Встроенный локальный чат

Добавление MCP не превращает существующий текстовый чат Ollama в агента автоматически. В этой версии MCP подключается к ИИ-клиенту, умеющему вызывать инструменты. Для встроенного чата потребуется отдельный цикл вызова инструментов, отображение предлагаемых действий и подтверждение пользователем операций изменения данных.
